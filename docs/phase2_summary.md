## 1. 概要

Phase 1で確立した因果推論の基礎（DAGに基づく交絡因子制御、駅徒歩・階数の効果推定）の上に、Phase 2では次の3つを行った。

1. **LLM特徴量の追加と、効果検証に基づく設計の全面改訂**（4節・9節）
2. **検証フレームワークの整備**：因果効果推定と予測モデルは目的が違うため検証方法を分け、頑健性チェック・K-fold CV・out-of-fold化を実装（5節）
3. **データ品質の作り込み**：CEMによる別手法での再検証（6節）、スクレイパーのバグ修正とフルDB再構築（7節）、部屋単位の重複掲載バグの発見と解消（8節）

一貫して「作った機能・仮説が実際に効いているかを検証し、効いていなければ手放す」という姿勢を取った。LLMの立地スコアはその代表例で、最終的に多重共線性が判明しモデルから除外している（9節）。

## 2. 最終結果サマリー（Phase 2完了時点）

7節・8節・9節の作業（データ基盤の全面再構築・部屋単位重複統合・location_scoreの除外）を経た最終状態。`location_score`はarea_groupとの深刻な多重共線性が判明したため、因果推論モデル・適正価格モデルの両方から除外した（9節）。

| 項目 | 値 |
|---|---|
| ②階数効果（建物固定効果） | +0.85%/階（p<0.001、ブートストラップCI [+0.65%, +1.14%]） |
| ①駅徒歩効果（building-level OLS） | -0.28%/分（p=0.119、非有意。ブートストラップCI [-0.68%, +0.18%]） |
| ①駅徒歩効果（CEM, area_groupなし） | -3.69%（ブートストラップ95%CI [-6.80%, +0.29%]、非有意） |
| ①駅徒歩効果（CEM, area_group込み） | +2.33%（ブートストラップ95%CI [-4.28%, +8.08%]、非有意） |
| 適正価格モデル R²（in-sample / out-of-sample） | 0.926 / 0.914 |
| 適正価格モデル N | 2,698部屋 |
| 適正価格モデル station_distance | -0.41%（通常SE p=0.0006 → building単位クラスターロバストSEでp=0.0622、非有意。注記参照） |
| 適正価格モデル brand_score（ルールベースtier, 1段階あたり） | +1.74%（p<0.001） |
| 割安（out-of-fold, 乖離率<-5%） | 1,033件 |
| 割高（out-of-fold, 乖離率>+5%） | 970件 |

Phase1時点の数値（旧データ・別スコープ）とは直接比較できないが、参考として：CEM area_groupなしのATTは旧データでは-5.80%（有意）だったのに対し、クリーンな渋谷区単体データでは-3.69%（非有意）に変化した。area_group込みのATTは-0.93%→+2.33%と符号が反転しているが、いずれも95%CIが0を跨ぐ非有意な推定であり、「符号が反転するほど推定が不安定＝このデータでは検出力不足」という解釈は変わらない。

**注記: ①駅徒歩効果、3手法すべてで非有意という結論に統一された**

適正価格モデル（room単位）だけstation_distanceが通常SEでp=0.0006と有意に見えていたが、`scripts/check_station_clustered_se.py`でbuilding単位クラスターロバストSEに直したところp=0.0622に後退し非有意になった（`brand_score`はp=0.0000→0.0010で頑健に有意のまま）。station_distanceはbuilding単位で不変の変数なので、9節でlocation_scoreに対して行ったのと同じ「room単位の通常OLSが標準誤差を過小評価する」問題が、除外前は気づかれていなかっただけでここにも当てはまっていた。

これにより、共変量調整OLS（building-level, p=0.119）・CEM（area_group込み, 95%CIが0を跨ぐ）・クラスター補正した適正価格モデル（p=0.0622）の3つの独立した手法すべてで「①駅徒歩効果は非有意」という結論が一致した。モデル選択の恣意性による見かけ上の食い違いではなく、データそのものの構造的特性に起因する可能性が高いと言える。

**解釈: なぜ渋谷区で駅徒歩効果が検出できないのか**

2つの要因に分解できる。

1. **検出力不足**: 渋谷区はJR各線・東急東横線・田園都市線・京王井の頭線・地下鉄各線が交差する高密度エリアで、区内のほとんどの物件がそもそも駅から近い側に偏っている。駅徒歩分数自体の分散が小さいため、統計的に効果を検出しにくい（Phase1時点から立てていた仮説。CEMを「駅近/駅遠」の二値に粗く分けざるを得なかったこと自体がこの制約の表れ）。
2. **エリアの質が駅距離を代理していた可能性**: `area_group`（町名）を制御すると効果がほぼ消えるという結果が一貫しているのは、「駅から近いこと」自体より「エリアの格・利便性」というより広い立地プレミアムが家賃を決めている可能性を示唆する。渋谷特有の構造として、駅前（道玄坂・宇田川町等の繁華街）が必ずしも高級とは限らず、松濤・南平台のような閑静な高級住宅地はむしろ駅からやや離れている。つまり「駅近＝高い」という単純な関係が渋谷では成立しにくく、エリアの質と駅距離が同じ方向を向くとは限らないという市場構造自体が、効果を打ち消し合っている可能性がある。

「真にゼロ」か「検出力不足」かの完全な切り分けはこのデータではできないが、①検出力不足の構造的な理由と②エリア質による代理の両方に心当たりがあり、単なる「渋谷は特殊だから」という曖昧な説明ではなく、具体的なメカニズムとして言語化できる状態になった。

## 4. LLM特徴量エンジニアリング

### 4.1 初期設計：brand_score・location_score（LLM推論、0-100連続値）

> **当時のスナップショット**：本項の数値は774建物時点のもの。設計自体は4.3節で全面改訂している。

物件名・住所から `brand_score`・`location_score`（各0〜100）を `gpt-4o-mini` で生成する設計から始めた。プロジェクト方針通り、部屋番号に依存しない建物単位の属性のため `rooms` ではなく `buildings` テーブルに追加した（`rooms.brand_score` は初期スタブとして残置、未使用）。

DBスキーマ（`buildings` に追加）:
```
brand_score     Float   LLMブランドスコア(0-100)
location_score  Float   LLM立地スコア(0-100)
llm_reasoning   Text    スコアの根拠（説明可能性のため保存）
llm_scored_at   DateTime  再実行時のスキップ判定に使用
```

**プロンプト設計上の重要な制約**：駅徒歩・築年数・階数・専有面積は既に因果モデルの変数として使っているため、**LLMにはこれらを一切評価させない**ようプロンプトで明示的に禁止した。これをやらないと `location_score` が `station_distance` と同じ情報を重複して持つことになり、モデルに投入したときに多重共線性を起こす。

評価観点は「デベロッパーブランド・シリーズとしての評価」（brand_score）と「駅距離を除いたエリアの格・治安・商業集積」（location_score）の2つに限定し、`temperature=0` で再現性を優先した。

**結果**（774建物全件スコア済み）:

| 指標 | 平均 | 標準偏差 | min | max |
|---|---|---|---|---|
| brand_score | 57.4 | 9.3 | 40 | 90 |
| location_score | 70.7 | 8.2 | 60 | 90 |

分布はやや狭い（LLMが極端な値を避ける典型的傾向）が、上位物件は「プラウド」「パークコート」等の大手ブランドライン、「渋谷・恵比寿・宇田川町」等の高評価エリアに集中しており、定性的に妥当だった。

**多重共線性チェック**（懸念していた駅距離・築年数との重複）:
```
corr(location_score, station_distance) = 0.072
corr(brand_score, age)                 = -0.161
```
どちらも十分小さく、この段階では「プロンプトの制約が機能している」と判断していた（後にarea_groupとの多重共線性が別に見つかる。9節）。

### 4.2 因果モデルへの統合と初期結果

> **当時のスナップショット**：本項の数値は669建物時点のもの。

`brand_score`・`location_score` を①駅徒歩効果モデル（building-level OLS）と適正価格モデル（log-logヘドニックモデル）の両方に共変量として追加した。

適正価格モデルへの影響:

| 変数 | 追加前 | 追加後 |
|---|---|---|
| `total_floors` | +0.22%（p=0.038, 有意） | +0.11%（p=0.313, **非有意化**） |
| `station_distance` | -0.32%（p=0.056） | -0.27%（p=0.104, **やや非有意化**） |
| `brand_score`（新規） | - | +0.16%（p=0.018, 有意） |
| `location_score`（新規） | - | +0.31%（p=0.037, 有意） |

`total_floors` が非有意化したのは、これまで「大規模・高級開発」の代理変数として拾っていた効果を `brand_score` がより直接的に説明するようになったためと解釈できる。ただし `total_floors` はDAG上 `floor` のバックドア（`floor ← total_floors → price`）を閉じる調整変数であり、**p値が非有意でも因果推論上は残すべき**（予測モデルの変数選択とは別のルール）。

`station_distance` がさらに非有意化したのは `location_score` との多重共線（駅近＝街の格が高い傾向）によるものと当時は解釈していたが、後の検証（9節）で `location_score` は `station_distance` よりも `area_group` と強く共線していることが分かった。

### 4.3 全面改訂：ルールベースbrand_score・順序尺度location_score・入力分離

**brand_score: LLM推論からルールベース分類へ**

大手・中堅デベロッパーのブランドラインは有限集合であり、LLMに推論させる必然性がないと判断し、`app/llm/brand_rules.py`の正規表現/部分文字列マッチングに置き換えた。旧プロンプトの「情報不足なら安全に中間値を返す」という挙動こそが、brand_scoreの分散が不自然に小さくなる直接の原因だった。ルールベース化により決定論的・完全再現可能・APIコストゼロ・ハルシネーションゼロを実現した。

ブランドは1〜5のティア（順序尺度）に分類し、tier5は「業界で言う大手3社（三井・三菱地所レジデンス・住友）の最上位ラインのみ」に厳格化、タワー特化ブランド（ブランズタワー等）は本体ブランドと同格のtier4に統一した。マッチングはパターン文字列長の降順で行い、「プラウドフラット」のような具体的な下位ブランド名が「プラウド」のような短い上位ブランド名より優先してマッチするようにした。

**location_score: 連続値→順序尺度、入力の分離**

0-100の連続値から、brand_scoreと同じ1-5の5段階順序尺度に変更し、OpenAI Structured Outputs（`json_schema` + `enum:[1,2,3,4,5]` + `strict:true`）で出力形式を保証した。

さらに、プロンプトに渡す入力を町名（住所の町丁目部分）のみに限定し、建物名・価格は一切見せない設計にした。同一コンテキストから2つのスコアを生成すると、LLMの「ハロー効果」により本来独立であるべき2変数間に人工的な相関が生まれ、回帰モデルに投入した際の見せかけの多重共線性の原因になるため。

### 4.4 ブランドティアの監査プロセス

ルール適用後のtier4/tier5全件に対する目視監査を経て、以下の誤判定を修正した。

- "ハイツ"等の汎用建物種別の接尾辞がtier2に誤って混入していた（tier1の定義（ブランド要素なし）の説明で挙げていた例そのものが、逆にtier2のパターンに入っていたという自己矛盾バグ）
- "パークマンション"（三井の最高峰ブランド）が、中黒区切りの無関係な一般名「〇〇パーク・マンション」に誤爆
- "ブリリア"が無関係な装飾語「ブリリアント」に前方一致で誤爆 → `NEGATIVE_PATTERNS`による除外機構を追加して対応

最終的にtier5=3件、tier4=72件、誤判定ゼロの状態を確認した上でスコアリングを完走した。

## 5. 検証フレームワークの追加

### 経緯

この時点では、因果推論・価格推定モデルのテストをしていなかったため追加。**重要な整理**として、このプロジェクトには性質の異なる2種類のモデルが同居している。

1. **因果効果推定**（②階数効果・①駅徒歩効果）: 目的は係数の正しさであって予測精度ではない。train/testで分割しても母集団の因果効果は変わらず、単にサンプルサイズが減ってCIが広がるだけ。必要なのは train/test ではなく**頑健性チェック**。
2. **適正価格モデル**（`build_fair_price_model`）: 正真正銘の予測モデル。ここに検証がなかったのは明確な欠陥だった。

### 5.1 因果効果推定の頑健性チェック（クラスターブートストラップ）

> **当時のスナップショット**：本項の数値は初期データ時点のもの。最新値は2節を参照。

OLSの標準誤差は正規性・分散均一性を仮定する。この仮定に依存しない頑健なCIを、building単位のクラスターブートストラップ（`app/analysis/matching.py: bootstrap_floor_effect / bootstrap_station_effect`）で算出した。

| | OLS点推定 | OLS 95%CI | ブートストラップ平均 | ブートストラップ95%CI |
|---|---|---|---|---|
| ②階数効果 | +0.57%/階 | [+0.40%, +0.74%] | +0.57〜0.60% | [+0.29%, +0.87%] |
| ①駅徒歩効果 | -0.24%/分 | [-0.79%, +0.32%] | -0.26% | [-0.88%, +0.32%] |

両方ともOLSとブートストラップの結果がほぼ一致。②は両CIとも0を含まず頑健に有意、①は両CIとも0を含み、**非有意なのはOLSの前提のせいではないことが確認できた。**CIの幅の広さ自体はデータの情報量が本質的に不足していることを示しており（真に効果がゼロなのか検出力不足なのかは未決着）、CEMなど別の識別戦略が必要という結論を補強する。

### 5.2 適正価格モデルのbuilding単位K-fold CV

> **当時のスナップショット**：本項の数値は初期データ時点のもの。最新値は2節を参照。

`C(area_group)` は町名によっては建物数が1〜2棟しかなく、固定効果がその建物固有の価格をほぼ「暗記」してしまうリスクがある。対策として、建物数が `MIN_AREA_GROUP_BUILDINGS=3` 未満の `area_group` は区レベル（例: `東京都渋谷区`）に自動統合した（29グループ中3グループが該当）。

その上で building 単位 5-fold CV（`evaluate_fair_price_model_cv`）で out-of-sample R²/RMSE を測定:

```
in-sample R²  = 0.931
out-of-sample R² = 0.911 (±0.018, 5-fold平均)
差 = +0.020 → 過学習は大きくない
out-of-sample RMSE(log_price) = 0.1598
unseen category除外 = 5fold中1件のみ
```

過学習が軽微であることが確認でき、モデル仕様（変数選択・関数形）自体は妥当と判断した。

### 5.3 本番スコアリングのout-of-fold化

> **当時のスナップショット**：本項の数値は初期データ時点のもの。最新値は2節を参照。

**CVはモデル仕様の診断であり、本番の `divergence_rate` の計算方法そのものは変えていない**という点が次の課題としてあった。従来は全データで学習したモデルで同じ全データを採点していたため、ある建物の価格が `C(area_group)` 等の固定効果を通じて自分自身の「適正価格」に混ざり込むリークが原理的に残っていた。

対処として、`compute_out_of_fold_scores()` を実装し、本番の `estimated_price`・`divergence_rate` を **out-of-fold予測**（building単位5-foldで、各建物は自分を含まないfoldで学習したモデルから予測を得る）に切り替えた。これは Double Machine Learning の **cross-fitting** と同じ発想で、「効果の解釈用の係数は全データ学習のまま、スコアリングだけ学習データと分離する」という役割分担にしている。

trainに存在しないカテゴリ水準（area_group等）を持つ行は該当foldでは予測できないため、全データ学習モデルによる in-sample 予測にフォールバックする設計にした（実績: 1,551件中1件のみ）。

**out-of-fold化の前後比較**:
```
                  in-sample      out-of-fold
割安(>5%)件数        542件           561件
割高(>5%)件数        510件           536件
```
件数がやや増えたのは劣化ではなく、out-of-fold予測は各foldで全体の約80%のデータしか使わないため（5-fold CVのout-of-sample R²=0.911がin-sample R²=0.931よりやや低いのと同じ理由）、モデルの精度が僅かに下がり、結果として乖離率のばらつきが大きくなったため。**より不確実性を正直に反映したスコア**になったと解釈できる。

**既知の限界**: out-of-fold予測は5つの異なるfoldのモデル（それぞれ別データで学習）から得られており、「1つの統一されたモデル」で採点しているわけではない。fold間のモデルのブレが追加ノイズとして混入する。リーク回避とのトレードオフとして許容している。

## 6. CEM（マッチング法）による①駅徒歩効果の再検証

> **当時のスナップショット**：本項の結果テーブルはフルDB再構築（7節）前の旧データ時点のもの。クリーンな渋谷区単体データでの最新結果は2節を参照（結論の方向性は変わらない）。

### 設計

`app/analysis/cem.py`。CEM（Iacus, King, Porro）は本来二値処置を前提とする手法のため、`station_distance`（連続・分）を中央値（6.0分）で「駅近(treatment=1)」「駅遠(treatment=0)」に二値化した。マッチング変数は `age`・`total_floors`・`avg_liv_area`（quantileベースの3分位ビン）と `building_type_cat`（厳密一致）。`area_group`（町名）を含める版・含めない版の両方を実行し、立地制御の有無による違いを比較した。

ATTは標準的なCEMの重み付け（`ATT = Σ_s T_s・(Ȳ_treated_s - Ȳ_control_s) / ΣT_s`、マッチ相手がいないストラータムは除外）で算出し、building単位クラスターブートストラップでCIを付けた。

### 結果（旧データ時点）

| | area_groupなし | area_group込み |
|---|---|---|
| ATT | **-5.80%**（駅近が家賃**安**） | -0.93% |
| ブートストラップ95%CI | [-12.17%, -1.55%]（**有意**） | [-10.80%, +6.12%]（非有意） |
| マッチ率（駅近/駅遠） | 99.7% / 98.6% | 41.7% / 39.9% |
| マッチ成立ストラータム | 34/37 | 61/282 |

### 解釈

**area_groupなしの結果（ATT=-5.80%, 有意）は符号が直感と逆**（駅近の方が家賃が安い）。これはOLSで繰り返し確認してきた「立地を制御しないと`station_distance`の符号が反転する」という現象を、CEMという全く別の（線形性を仮定しない）手法でも再現したものであり、**立地の交絡を制御しないと自信満々に間違った結論に至る**ことを具体的な数値で示す好例になった。

**area_group込みの結果（ATT=-0.93%, 非有意）はOLS+ブートストラップの推定（-0.24%/分, 95%CI[-0.88%,+0.32%]）と整合的**。単純OLS→共変量調整OLS+ブートストラップ→CEMという3つの独立した手法すべてで「立地を適切に制御すると①駅徒歩効果は検出できない」という同じ結論に達した。ただし`area_group`を厳密一致に含めるとマッチ率が41.7%まで低下し（ストラータムの組み合わせ数がサンプルサイズに対して爆発する「次元の呪い」）、**「真に効果がゼロ」なのか「サンプル不足で検出力が足りないだけ」なのかは、このデータでは切り分けられない**。

## 7. データ基盤の全面再構築

### 7.1 新宿区追加とその撤回

CEM（6節）の`area_group`込みマッチ率の低さを解消するため、対象エリアに新宿区を追加する案を検討・着手したが、実装途中で2つの問題に気づき撤回した。

1. `area_group`は町名ベースの厳密一致ストラータムであり、新宿区のデータは渋谷区の既存ストラータムと町名が重ならないため、追加してもストラータム不足そのものは解消しない。エリア拡張で解決すべき問題ではなく、渋谷区単体でのデータ密度向上（同一町名内の建物数を増やす）が本質的な対応だった。
2. LLM採点（location_score）が複数日にわたって行われ、その間にプロンプト仕様変更（0-100連続値→1-5段階、入力を町名のみに限定）を挟んでいたため、新宿区データと渋谷区データで採点基準が混在するリスクがあった。

この2点から新宿区は対象から外し、渋谷区単体に絞る方針に転換した。

### 7.2 スクレイパーの建物名抽出バグ修正

割安トップ10とは別に、`check_data_quality.py`の重複診断で建物の名寄せ漏れ（同一建物が複数の`building_id`に分裂）が大量に見つかり、原因を調査した結果、3種類の抽出バグが判明した。

1. 建物名が未設定の物件で、`h1`要素に「駅名+階建+築年数」の汎用要約文が入り、これがタイトルとして抽出される。`is_generic_title()`で判定し、該当する場合は住所+総階数+築年数の複合キーを名寄せのフォールバックに使うよう変更した。
2. 同一建物名のローマ数字/算用数字表記ゆれ（「〇〇II」と「〇〇2」）。`normalize_roman_suffix()`で正規化。
3. マーケティング文言が建物名の前後に付着し、本来同一の建物名が微妙に異なる文字列になる。名寄せ時に空白除去後の部分文字列関連性チェックで同一建物と判定するよう対応。

`scripts/backfill_dedup_buildings.py`で既存データに対する統合を実施し、都度ダミーラン→適用で確認した。

### 7.3 フルDB再構築とスキーマ追加

建物名抽出バグの修正とスキーマ変更を反映するにあたり、旧スキーマ時代のデータが混在するリスクを避けるため、DBを一度全消去（`scripts/reset_db.py`）した上で、渋谷区163ページ分を`--start-page`指定なしで全件再スクレイピングした。スクレイパーの upsert 設計（`suumo_room_id`のユニーク制約・建物側の複合キーによる名寄せ）が冪等であることを前提に、途中のページ番号から再開するのではなく必ずページ1から全件を取り直す方針にした（Suumoの掲載順が日によって変動するため、途中再開だと欠損・重複のリスクがある）。

再構築時にDBスキーマへ以下の4カラムを追加した（`alembic/versions/d5e6f7a8b9c0_...py`）:

```
buildings.total_units    総戸数（取得率30.6%、欠損時はNULL許容）
rooms.orientation        向き
rooms.move_in_date       入居可能日
rooms.url                元listingのURL（8節の重複調査で活用）
```

## 8. 部屋単位の重複掲載バグの発見と解消

### 発見の経緯

`run_analysis.py`の割安トップ10に、建物名・階・専有面積・間取り・価格が完全一致する部屋が複数回出現する事象を発見した。`scripts/debug_duplicate_rooms.py`で該当行の`suumo_room_id`・URLを確認したところ、いずれも異なる掲載（別々の`suumo_room_id`・URL）だった。実際のURLをブラウザで開き目視確認したところ、取扱店舗（不動産会社）が異なる一方で、部屋番号・間取り図・写真は同一であることを確認し、同一の物理的な部屋が複数の不動産会社経由で重複掲載されていることが確定した（一部のケースでは管理費や契約形態も店舗ごとに異なっていた）。

これは`check_data_quality.py`の既存の重複診断（`COUNT(DISTINCT building_id) > 1`を要求）では検出できない盲点だった。同一`building_id`内での重複のため、この診断ロジックの対象から外れていた。

### 対処

`scripts/backfill_dedup_rooms.py`を新設し、`(building_id, floor, liv_area, floor_plan)`を同一物理部屋の候補キーとして以下のルールで統合した。

- キー内の価格が単一（またはNULLが混在するだけ）なら全体を1件に統合する。
- 価格が複数混在する場合は、価格ごとのサブグループに分割し、2件以上一致するサブグループのみ統合する（1件しかない価格やNULLは「判別不能」として統合せず残す、安全側の設計）。
- 統合時に残す代表行（canonical）は、`monthly_fee`（price + admin_fee）が最も安いものを採用する。同一物件でも取扱店舗によって管理費が異なるケースが実際に確認されており、「実際に借りるなら合計額が最も安い条件を選ぶはず」という考え方に基づく。

初回実装では「キー内に価格の異なる行が1件でも混ざっていると、そのキー全体の統合がブロックされる」という設計上の不備があり、これによりテアトル神南など本来統合できたはずの完全一致ペアが未統合のまま残っていた（キー内訳: 245,000円が2件・290,000円が1件、といった構成で、290,000円の1件の存在だけで245,000円の明確な重複ペアまで巻き添えでブロックされていた）。サブグループ単位の判定に修正し、再適用して解消した。

最終的に2回の適用（1,367グループ/1,898件 → 追加260グループ/260件）で計2,158件の重複roomを削除し、割安トップ10の完全一致重複を解消した。

### 副次的な発見

重複除去の前後で、適正価格モデルの`location_score`係数が `-2.24%〜-3.01%`（p=0.012〜0.026, 有意）から `-2.22%`（p=0.074, 非有意）に変化した。符号は依然として負のままで完全な解決ではなかったが、重複データによるノイズが有意性の一部を作り出していた可能性を示唆した。この符号問題の全面的な検証と最終結論は9節を参照。

## 9. location_scoreの符号問題の最終検証とモデルからの除外

8節で見つかった`location_score`の反直感的な負係数について、3種類の診断で多角的に検証し、最終的にモデルから除外する判断を下した。

### 検証1: VIF・クラスターロバストSE・area_group除外時の符号変化（適正価格モデル, room単位）

`scripts/debug_location_score_collinearity.py`。

| 診断 | 結果 |
|---|---|
| VIF（分散拡大係数） | `location_score`=**12.04**（他の変数は1.14〜3.67）。VIF>10は深刻な多重共線性の目安 |
| building単位クラスターロバストSE | `location_score`のp値が 0.074 → **0.285** に後退（`brand_score`・`floor`等は頑健なまま有意を維持） |
| `area_group`を外した場合 | `location_score`の係数が -2.22%（非有意）→ **+10.17%**（p<0.001, 高度に有意）に符号反転 |

クラスターロバストSEの検証は当初の想定外の副産物だった。`brand_score`・`location_score`・`station_distance`等はbuilding単位で不変の変数なのに、room単位の通常OLSはroomを独立観測として扱うため標準誤差を過小評価する（実質的な独立情報量はroom数ではなくbuilding数に近い）。

### 検証2: area_groupをlocation_scoreに置き換えた場合の性能比較

`scripts/debug_area_group_vs_location_score.py`（matching.py, 因果推論用, building単位）と`scripts/debug_area_group_vs_location_score_scoring.py`（scoring.py, 予測用, room単位）の両方で、「現状（両方）」「area_groupのみ」「location_scoreのみ」の3パターンを比較した。

| モデル | 指標 | 現状(両方) | area_groupのみ | location_scoreのみ |
|---|---|---|---|---|
| matching.py（①駅徒歩効果） | station_distance | -0.28%(p=0.118) | -0.28%(p=0.119) | -0.17%(p=0.332) |
| | R² / AIC / BIC | 0.926 / -799.0 / -606.3 | 0.926 / **-801.0** / **-613.3** | 0.912 / -648.7 / -603.1 |
| scoring.py（適正価格モデル） | in-sample R² | 0.926 | 0.926 | 0.908 |
| | out-of-sample R² / RMSE | 0.914 / 0.1658 | 0.914 / 0.1659 | 0.900 / 0.1784 |

`area_group`を`location_score`で置き換えると、因果推論・予測いずれのモデルでも全指標（R²・AIC・BIC・out-of-sample性能）が悪化した。さらに`area_group`が既にある状態に`location_score`を追加しても、in-sample R²・out-of-sample R²は小数第3位まで完全に同値で、AIC/BICもほぼ引き分け（両方入れた方がAICはわずかに良く、BICはarea_groupのみの方がわずかに良い）。つまり`location_score`は`area_group`が存在する場面で実質的な寄与をゼロにしていた。

### 経緯の訂正（時系列の確認）

時系列の妥当性を再検証するため、ファイルの更新日時とalembicマイグレーションの日付を実際に確認して裏取りした。正しい時系列は次の通り。

```
2026-08-13  phase1_summary.md: area_group導入済み。「次段階はCEMで検出力向上」と明記
2026-08-15  brand_score/location_score カラム追加（location_score誕生）
2026-08-22〜23  matching.py/scoring.py/cem.py 実装（CEMはこの時点で初めて実装）
```

つまり`area_group`はPhase1（8/13以前）から存在し、`location_score`はその後8/15に「`area_group`とは独立な補完情報を追加する」意図で追加された。CEMの実装（8/23）はさらにその後であり、CEM設計時点で`location_score`は既に存在していたが、CEMのストラータムには一貫して`area_group`のみが使われ、`location_score`が使われたことは一度もない。これが意図的な判断だったのか単なる見落としだったのかを示す記録は残っていない。

### 結論と対応

`location_score`は元々「町名のみ」を入力にしていたため、`area_group`（町名を直接ダミー変数化した固定効果）と本質的に同じ情報源から作られており、当初期待していた「独立な補完情報」にはならなかった。多重共線性の教科書的な症状（個々の係数は不安定化するが、モデル全体の予測力を大きく損なうわけではない）そのものだったが、`location_score`単体の追加効果を複数の指標で測定した結果、実質的な寄与はゼロと判断できた。

対応として、`location_score`を`app/analysis/matching.py`（`STATION_EFFECT_FORMULA`）・`app/analysis/scoring.py`（`FAIR_PRICE_FORMULA`）の両方から除外した（2026-08-26）。`brand_score`はVIF=1.37と問題なく、両モデルに引き続き有意に寄与している（適正価格モデルで+1.74%, p<0.001）ため残した。`location_score`自体はDBカラム・LLM採点パイプラインとしては記録目的で残置しているが、モデルには使われていない。

除外後の再検証（`scripts/run_analysis.py`）:

| 変数 | location_score込み | location_score除外後 |
|---|---|---|
| 適正価格モデル station_distance | -0.43%(p=0.0004) | -0.41%(p=0.0006) |
| 適正価格モデル R²（in-sample/out-of-sample） | 0.926/0.915 | 0.926/0.914 |
| 適正価格モデル brand_score | +1.72%(p<0.001) | +1.74%(p<0.001) |
| 割安（out-of-fold, >5%） | 1,046件 | 1,033件 |
| 割高（out-of-fold, >5%） | 942件 | 970件 |

主要な係数・R²・過学習の程度に実質的な変化はなく、`location_score`除外がモデルの質を損なっていないことを確認した。

## 10. 残っている課題（Phase 3以降）

- **①駅徒歩効果の非有意性**: 共変量調整OLS・CEM・クラスター補正した適正価格モデルの3手法すべてで非有意という結論に統一された（2節注記）。`area_group`を含めるとマッチ率が大きく落ちるため、「真にゼロ」か「検出力不足」かは未決着。根本対応はエリア拡張によるサンプル増加。
- **未観測仕様交絡（築古×リノベ/ヴィンテージ）**: `age` の符号自体はPhase1で修正済みだが、年数だけでは「リノベ済みヴィンテージ物件」と「未改装の築古物件」の価格差を説明できない欠落変数バイアスは残る。
- **building_structureが未使用のまま**: `building_structure`（RC/鉄骨/木造等）は当初取得率が低く、`age`/`total_floors`によるプロキシ補完で運用する設計だった。その後スクレイパー側の抽出バグ（`th.data_02`という別クラス体系での提供に対応できていなかった）を修正しており、現在は1,925建物全件（100%）取得できている（`scripts/check_building_structure_rate.py`で確認済み）。ただし因果推論モデル・適正価格モデルのいずれにもまだ変数として組み込んでいない。構造による価格差は交絡因子として無視できない可能性があり、追加検証の余地がある。
- **契約形態（普通借家/定期借家）の未取得**: 重複掲載の調査中に、同一物理部屋でも取扱店舗によって契約形態・管理費が異なるケースが見つかった。定期借家は一般に賃料が下がる傾向があり、データセット全体で系統的な交絡因子になる可能性がある。`rooms.url`を保存済みのため、フルスクレイピングをやり直さずに既存URLを再訪して後から埋めることが可能。
- **地価データ・PostGIS統合**: 今回のスコープでは見送った。PostgreSQL 15を採用しているのはこの拡張を見据えたためで、町名固定効果（`area_group`）より連続的な地理情報を使えば、より精緻な立地プレミアムの制御ができる可能性がある。
- **予測性能の高度化**: LightGBM等の決定木系モデルで非線形・交互作用を捉え、残差ノイズを抑制する。
- **out-of-fold予測のfold間ブレ**: repeated K-fold（異なる分割を複数回行い平均する）で軽減できる可能性がある。

## 11. 設計判断の要点と技術的知見

- **LLM特徴量設計での多重共線性対策**: プロンプトで「既に分析済みの変数（駅距離・築年数）を評価に含めるな」と明示し、実際に相関係数で検証（0.07・-0.16）した。LLM特徴量を因果/回帰モデルに組み込む際の典型的な落とし穴（プロキシ変数の重複）を設計段階で回避した例。
- **予測モデルと因果効果モデルで異なる検証戦略を採用**: 「なぜtrain/testをしていないのか」という指摘に対し、因果効果推定（母集団パラメータの推定）と価格予測（個別予測性能）は検証の目的が異なることを整理し、前者にはクラスターブートストラップ、後者にはK-fold CV + out-of-fold cross-fittingを使い分けた。
- **Cross-fitting（Double ML由来）の適用**: 本番スコアリングにおける「学習データ=推定データ」問題を、Double Machine Learningのcross-fitting同様の発想（効果推定用モデルとスコアリング用モデルを分離）で解決した。
- **リークに気づいて設計を直したプロセス**: `C(area_group)` の少数グループが自分自身の価格を暗記してしまうリスクにCVだけでは気づけないことを認識し、out-of-fold化という一段深い対策に踏み込んだ。
- **単一手法に依存しない頑健性の示し方**: ①駅徒歩効果について、関数形の仮定が異なる3つの手法（OLS／ブートストラップ／CEM）で一貫して同じ結論（非有意）に到達したことを示し、「モデルの選び方次第で結論が変わる」という再現性リスクを潰した。同時に、`area_group`の有無でCEMの結果が劇的に変わる（符号自体が反転する）という事実自体を、交絡制御の重要性を示す教材として提示できる。
- **データ量拡大の前に品質を診断する判断**: 「先にサンプルを増やすか、先に既知のバグを直すか」という場面で、後者を優先した。名寄せが崩れた状態でサンプルだけ増やしても、モデルの係数が歪んだまま検出力だけが上がる（＝間違った結論に自信を持ってしまう）リスクがあるため。
- **再現率より適合率を優先した名寄せ設計**: 建物名寄せ・部屋の重複統合のいずれも、「怪しいものは全部統合する」ではなく「確信が持てるものだけ統合し、判断がつかないものは残す」設計を一貫して採用した。データが多少残っても後で個別に精査できるが、誤って別の物件を統合してしまうと後から気づくのが難しいという非対称性を踏まえた判断。
- **地域拡張が根本解決にならないと気づいて撤回した判断**: CEMのストラータム不足を解消するために新宿区追加に着手したが、`area_group`が町名ベースの厳密一致キーである以上、新宿区のデータは渋谷区の既存ストラータムを一切補強しないと判明し、実装途中で撤回した。「サンプルを増やせば大抵の問題は薄まる」という直感に反する判断を、キーの定義に立ち返って検証した例。
- **1つのgranularityでの重複チェックでは不十分だと認識した経緯**: 建物単位の名寄せ（`COUNT(DISTINCT building_id)>1`）だけでは、同一建物内での部屋単位の重複掲載を検出できないという盲点があった。粒度の異なる重複が別々のバグとして存在しうることを、実際のトップ10の異常値から逆算して発見した。
- **「1件の例外が集合全体をブロックする」設計バグの自己発見と修正**: 重複統合ロジックの初回実装では、価格が食い違う行が1件混ざっているだけでグループ全体の統合を諦めていた。実データ（テアトル神南）で本来統合できるはずのペアが残っているのを見て、サブグループ単位の判定に設計を修正した。安全側に倒したつもりの設計が、逆に安全な統合まで巻き添えでブロックしていたケース。
- **自分の作った特徴量を、証拠に基づいて手放した判断**: `location_score`はPhase2の目玉として設計したLLM特徴量だったが、VIF・クラスターロバストSE・area_group置き換え比較（AIC/BIC/out-of-sample性能）という複数の独立した診断すべてが「area_groupがある場面では実質的な寄与ゼロ」と一致して示したため、因果推論モデル・予測モデルの両方から除外した。労力をかけて作った機能でも、データが「効いていない」と言うならそれに従うという、サンクコスト回避の実例。
- **自分の説明の誤りを、記憶ではなくファイルの証拠で検証して訂正したプロセス**: 記憶に頼って判断するのではなく、ファイルの更新日時とalembicマイグレーションの日付を実際に確認して裏取りした。
- **駅徒歩効果の非有意性の具体的なメカニズム**:①高密度な鉄道網によるtreatment変数（駅徒歩分数）自体の分散不足という検出力の問題と、②`area_group`を制御すると効果が消えることから示唆される「駅距離はエリアの質のプロキシに過ぎない」という解釈の2つに分解して説明できた。あわせて、適正価格モデルだけがstation_distanceを有意と示していた食い違いも、location_scoreと同じクラスタリング起因の標準誤差過小評価だと突き止め、3手法の結論を一致させた。
